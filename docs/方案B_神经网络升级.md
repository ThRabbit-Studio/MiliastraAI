# 方案 B：换成真的小神经模型（替换点与可行性）

> 本文是"下一步"的施工方案，不是当前已交付的内容。当前交付的是方案 A（检索 + 模板重组）。
> 目标：让答句真的由一个小型神经网络逐字算出来，观感上就是 B 站那个"离线 AI 在一字一顿地算"。

---

## 1. 为什么必须小：先算清天花板

Lua VM 里做浮点乘加的吞吐量级约 **2000–5000 万次/秒**（本机实测同样量级，真机 CPU 更弱）。

一次前向的乘加量 ≈ `2 * 层数 * d_model²` + `d_model * 词表`（输出层）：

| 配置 | 参数量 | 每字乘加 | 每字耗时 | 30 字回复 |
|---|---|---|---|---|
| `d=64, L=2, V=1500`（超轻） | 约 14 万 | 约 12 万 | 约 3 ms | 约 0.1 s |
| `d=96, L=2, V=2500` | 约 57 万 | 约 26 万 | 约 8 ms | 约 0.25 s |
| `d=128, L=4, V=3000` | 约 170 万 | 约 79 万 | 约 25 ms | 约 0.75 s |
| `d=192, L=4, V=4000` | 约 370 万 | 约 176 万 | 约 55 ms | 约 1.7 s |
| `d=256, L=6, V=6000` | 约 1050 万 | 约 440 万 | 约 140 ms | 约 4.2 s ← 已经不能用 |

**结论：参数量上界约 400 万。** 这不是"模型越大越强"的地方，性能是硬墙。B 站那位作者停在 246 万参数，就是这个原因。

再考虑逐帧预算：每帧最多花 1–2 ms 做推理（其余留给渲染），所以
- 每字 8 ms → 需要 4–8 帧 → 60fps 下每字 0.07–0.13 秒
- 30 字回复 → 2–4 秒。**这个节奏正好就是"逐字在算"的观感，不需要假装。**

## 2. 模型与训练

**架构**：字符级（char-level）微型 Transformer 或纯 2 层 MLP-LM（带 4~8 个历史字符的窗口）。
字符级比子词简单得多，且中文单字本身信息量足够，适合这个规模。

**训练数据**：中文单轮对话语料 + 本项目的 `data/questions.json`。
本机 PyPI 不可达，需要离线获取；也可由 LLM 生成几千条目标风格问答（人设一致、短句、口语），质量比公开闲聊语料更可控。

**词表**：约 2000–4000 字（取语料覆盖 99.9% 的字），加 `<pad> <bos> <eos>`。

**训练放在 Python 侧（PyTorch，CPU 足够）**，训练完后做两件事：
1. **量化**：int8 + 每输出行一个 float 缩放系数（`w[i] ≈ q[i] * scale[row]`）。
   这样点积可以全用整数累加，最后一次乘 scale，Lua 侧开销最小。
2. **导出**：把 int8 权重编码成 ASCII 安全字符串常量写进 `main.lua`。
   用十六进制（每字节 2 字符）而不是 base64，编码解码逻辑更简单、也不涉及平台编码问题。

体积参考：50 万参数 int8 = 500 KB 二进制 = **1 MB 十六进制文本**。
所以模型规模要和"源码体积"一起权衡，必要时把权重拆到独立客户端脚本（`control:GetScriptByPath` 取回来），但那条路在文档里没有写明脚本间能否取到数据，**需要真机验证后才能用**，第一版建议单文件。

## 3. Lua 侧推理骨架

```lua
-- 每帧只做一步，绝不整句一次算完
function on_frame(dt)
    if ST.gen_state then
        local budget = CFG.INFER_MS_PER_FRAME
        local t0 = os.clock()
        while os.clock() - t0 < budget and not ST.gen_state.done do
            token_step(ST.gen_state)     -- 算一个字符
        end
        if ST.gen_state.done then
            ST.reply = ST.gen_state.text
            ST.gen_state = nil
            -- 接着走逐字显示
        end
    end
    ...
end
```

关键点：
- 用 `os.clock()`（沙箱允许）做时间预算，而不是固定步数，这样不同性能的机器都能自适应；
- 历史窗口只保留最近 8~16 个字符，注意力/上下文开销恒定；
- 采样用温度 + top-k，避免重复循环（小模型的典型毛病）。

## 4. 怎么保证移植不出错（这是最容易翻车的地方）

三层对齐，逐层收敛：

1. **Python 参考实现**：训练后立刻用 numpy 手写一遍前向，与 PyTorch 输出逐 token 对比（要求一致到 1e-5）；
2. **量化前后对比**：量化后再跑一遍，比较 top-5 候选与概率偏差，记录可接受的退化；
3. **Lua 与 Python 对齐**：把同一段输入喂给两边，逐 token 比较输出字符串。这一步可以挂在现有 `verify/t_harness.py` 里，作为新的场景。

**只有在第 3 步通过之后，才谈能不能进关卡。** 前面两层用 numpy/lupa 在本机就能跑，不需要原神。

## 5. 与现有代码的接口

替换点非常干净，UI/输入/候选/逐字渲染完全不用动：

| 现在 | 换成 |
|---|---|
| `compose(seed, id, typedLen)` 从语料变体里组句 | `generate(seed, prompt)` 调模型逐字生成 |
| `query()` 候选匹配 | **保留**（模型负责生成答句，候选检索仍然比模型可靠） |
| `MOD.ANSWERS` 语料 | 退化为"训练数据"或"兜底话术"，仍保留 |

也就是说：**方案 A 的输入、候选、渲染、性能调度全部是方案 B 的地基，不是临时脚手架。** 现在这套东西跑通之后，换模型的改动面只有 `compose()` 一个函数。

## 6. 风险与预案

| 风险 | 预案 |
|---|---|
| 小模型说胡话、重复字 | 温度 + top-k + 重复惩罚；保留方案 A 作为可切换的"稳妥模式" |
| 单帧超预算导致掉帧 | 时间预算自适应 + 每帧步数上限；实测超过 25 ms/字就退回方案 A |
| 权重文本过大导致脚本加载慢 | 缩小词表/维度；或改为只加载一次并缓存 |
| 真机 Lua 与 lupa 的数值差异 | 全部用整数累加 + 最后乘 scale，避免平台浮点差异被放大 |
| 训练语料不够 | 先用 LLM 批量生成目标风格问答，人工抽检 5% |

## 7. 需要先解决的前置条件

1. **PyTorch 未安装**，且本机 PyPI 连不通（连接被重置）→ 需要离线 wheel 或换一台机器训练；
2. **脚本间能否取到权重数据未验证** → 第一版走单文件；
3. **真机性能未知** → 现在的 `os.clock()` 探针可以直接在真机日志里输出每字耗时，用真机数据校准模型规模，而不是靠估算。
